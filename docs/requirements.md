# CallBar Favorites and Call History

**Review draft · 23 November 2026.** “Recents” is the Call History tab. B and O identify the documented baseline and observation limits. F, H and P identify scenarios and shared behavior. Q identifies a product decision. All eight product decisions (Q1–Q8) are confirmed. The mockups illustrate alternatives. The scenarios and acceptance criteria describe the intended release behavior. The [local acceptance record](#favorites-local-acceptance) covers F1–F6.

## What CallBar can observe

| ID | Event | What the user can reliably be told |
| --- | --- | --- |
| O1 | CallBar validates the input, receives an explicit call action and begins an outgoing request. | CallBar knows the requested number and the local request time. Invalid input produces an input error before any handoff. Pasting, selecting, or saving a number is not a call attempt. |
| O2 | The documented handler check finds no app for phone links, or the request to open the link fails. | “No calling app available” when the check establishes that fact, otherwise “Couldn’t open calling app.” Both are local failures. An unavailable iPhone or a busy recipient cannot be diagnosed this way. |
| O3 | macOS reports that the phone URL opened successfully. | “Sent to calling app.” The registered handler can be a third-party app. Its later confirmation, cancellation, iPhone availability, ringing, answer, decline, missed call, duration, and end time are outside this handoff. Incoming calls and calls initiated elsewhere are outside this history. |
| O4 | CallBar exits before observing the result. | The result is unknown. Never turn an interruption into success or failure or automatically repeat the request on launch. |

Apple defines success here as opening a URL. A system confirmation can still be canceled afterward. The project documents real-device call acceptance as pending. [Apple AppKit URL opening](https://developer.apple.com/documentation/appkit/nsworkspace/open(_:)), [CallBar architecture](architecture.md), [verification record](verification.md)

## Shared behavior and proposals

- **P1 · Navigation.** Open on Dialer with the number field focused. Use Dialer, Recents, and Favorites within one popover. Browsing a tab preserves the current dialer draft. Choosing a specific number replaces that draft. Merely navigating, opening Setup, or reopening the popover never initiates a request. The tab order is Dialer, Recents, Favorites (Q4).
- **P2 · Number identity.** Use the documented dialer rules everywhere. Strip supported formatting and surrounding whitespace. Accept 3–15 ASCII digits with an optional leading plus, preserve leading zeros, and reject embedded newlines, extensions, URLs, and unsupported characters. For example, `(020) 123-4567` and `0201234567` match. `+44201234567` remains distinct. Never infer a country. Match by the normalized number, independently of the label.
- **P3 · Storage and recovery.** Both lists must persist locally for the current Mac user (Q3). A completed save, edit, or deletion survives app restart. Unsaved edits and the dialer draft are session-only. A failed write preserves the last committed data and offers a retry. A read failure shows a recovery message with Retry and disables mutations for the affected list. Do not present unreadable data as an empty list or overwrite it. A history write failure after handoff is reported separately; retrying the write must never redial. Keep numbers out of analytics and diagnostic logs.
- **P4 · Interaction boundaries.** Each deliberate call action creates at most one handoff. Guard against a double click, key repeat, or overlapping requests from different tabs while a request is pending. When it finishes, a fresh explicit activation can call the same number again. Close and reopen never replays an action. In an editor, Enter saves and Esc cancels. In a list, keyboard activation follows the same selection policy as a mouse click. Label star, call, edit, and delete controls with the target number or name for VoiceOver.
- **P5 · Cross-tab identity.** Each recent event keeps the exact normalized destination and request time. Look up the current favorite name by that number when rendering a row. Renaming a favorite updates matching rows. Changing its number moves the favorite association to the new number. Removing it exposes the original numbers in Recents. Saving, editing, or deleting a favorite never creates an attempt. A number already loaded in Dialer stays available as an independent draft.
- **P6 · Pending and interrupted requests.** Record one attempt when CallBar accepts an explicit Call or Enter action for a number that passed validation (Q1). Capture the number and timestamp at that point, before checking the handler or opening the phone link. An observed local result updates that same entry. A previously saved pending entry becomes “Result unknown” after an interrupted session. If the process exits before any entry is saved, recovery cannot reconstruct the attempt. Deleting an attempt or clearing history while a result is pending suppresses late reinsertion. A genuinely new attempt after clear may appear.

## Recents scenario review

Show each accepted call action in its own row, newest first. Group rows by the local date of the action, using **Today** and **Yesterday** as in the sketch. For earlier days, use a calendar date. Put the time on the second line. A saved favorite shows its name above the number and time (for example, **Alex** above `+1 202 555 0102 · 11:42 AM`). An unsaved number shows the number above the time alone (for example, `9:18 AM`). Use the Mac’s local time format. The observed handoff result can update independently of the recorded time. Two events with the same displayed minute remain individually addressable. Opening an older entry always uses its original destination.

## Decision register

### Confirmed decisions

| ID | Decision | User-visible consequence |
| --- | --- | --- |
| Q1 | Record an attempt once validation passes and CallBar accepts the explicit call action. Enter in Dialer is the keyboard equivalent of Call. | A valid number sitting in the field creates no history. After activation, a missing handler or failed handoff still leaves one attempt in Recents. |
| Q2 | Activating a Favorites or Recents row loads its destination into Dialer for review. | The user can edit the number, then press Call or Enter as a separate action. Selection alone causes zero handoffs and zero new attempts. |
| Q3 | Store both Favorites and Recents locally for the current Mac user across app restarts. | The same Mac user can reopen the app and find saved favorites and recorded attempts, including local handoff failures. |
| Q4 | Use three tabs in order: Dialer, Recents, Favorites. Open on Dialer. | Both lists have their own space in the popover. |
| Q5 | Require a name when saving a new favorite. Keep one favorite per normalized number. | Starring a new number prompts for its name. Starring the same number again opens the saved entry. |
| Q6 | Give each accepted call action its own chronological row with the date heading and event time shown as in the sketch. | Repeated calls to one number remain individually selectable and removable, even within the same displayed minute. |
| Q7 | Require confirmation for every user-initiated deletion of a favorite or recent attempt and for clearing either list. Cancel is the default. | The single-entry dialog identifies the selected entry. The clear dialog names the list and shows its count. Confirm applies only to that target. |
| Q8 | Keep the latest 100 recorded call attempts for this Mac user, in activation order. | When a new attempt takes Recents over the limit, automatically discard the oldest attempt without a confirmation dialog. Repeat numbers and local handoff failures each count. Favorites has no history-based expiry. |

## Acceptance criteria for confirmed decisions

| ID | Decision | Given / when | Required result |
| --- | --- | --- | --- |
| T1 | Q1 | Start with empty Recents. Paste a valid number and wait. Activate Call once with the handoff result delayed. | Zero entries before activation. One attempt with the dialed digits and activation time while the result is pending. Receiving the result updates that attempt once. |
| T2 | Q1 | Try Enter with an empty field and an invalid number. Then enter a valid number and press Enter with no handler available. | The first two actions produce zero attempts. The third produces exactly one attempt and reports the missing handler. |
| T3 | Q2 | In turn, click a favorite and keyboard-activate a recent row. Inspect Dialer after each selection. Then edit the loaded digits to a different valid number and explicitly press Call. | Each selection loads the corresponding number, sends zero requests and adds zero events. The final action sends one request and records the edited number. |
| T4 | Q1, Q3 | Save a favorite, make two valid attempts (one accepted by macOS, one rejected), quit, and relaunch as the same user. | The favorite and both attempts are available with their original destinations, times and observed results. Relaunch causes zero new requests and zero additional events. |
| T5 | Q4 | Launch CallBar, open the popover, type a number, and visit Recents and Favorites without selecting a row. Return to Dialer. | The three tabs appear in the agreed order. Dialer opens first, the typed number is available on return, and browsing creates zero attempts. |
| T6 | Q5 | Star an unsaved number in Recents. Try saving a whitespace-only name, then enter Alex and save. The second star opens Alex’s existing entry. |
| T7 | Q6 | Make three deliberate attempts to Alex, including two during the same minute. For one attempt, delay the handoff result until the next minute. | Recents contains three separately selectable rows. Each shows Alex above the number and activation time. Receiving the delayed result changes neither its displayed minute nor its order. |
| T8 | Q6 | In a 12-hour locale, record an unnamed number at 11:59 PM, then Alex at 12:01 AM the next day. Open Recents and relaunch later that morning. | Both views show Alex under Today with number and 12:01 AM on the second line. The unnamed number appears under Yesterday with 11:59 PM below it. Once older, an event moves under its calendar date and retains its time. |
| T9 | Q7 | With two favorites and two recent attempts to the same number, request deletion of one favorite. Repeat for one attempt. For each target, first dismiss with Esc, then reopen and confirm. | Each dialog identifies its target and defaults to Cancel. Dismissal preserves both lists. | T10 | Q8 | Start with 99 attempts and the oldest number saved as a favorite. Record a 100th attempt. The 101st attempt automatically replaces only the oldest entry. Attempts 2–101 persist in newest-first order, including the new failure, and the saved favorite is still available. |
| T11 | Q3, Q8 | With 100 committed attempts, simulate a storage failure when recording the next attempt. Retry the history write after storage recovers. | The failed write preserves the 100 committed rows. Successful retry records the new attempt once and evicts the oldest once. Retrying storage sends zero additional call requests. |

## Cross-scenario acceptance checks

These checks cover interactions across tabs, storage errors, and interrupted requests.

| ID | Given / when | Expected result |
| --- | --- | --- |
| AC1 | Save Front desk as `(020) 123-4567`, then star `0201234567` from Recents. | One favorite exists. Its editor opens with Front desk. Both spellings load `0201234567`; the leading zero survives relaunch. |
| AC2 | Double-click Call while the first request is pending; after it finishes, deliberately redial the same number. | Two handoffs total, two events with separate identities. Deleting the older event and relaunching leaves the newer event and the favorite. |
| AC3 | Open a phone URL successfully, then cancel confirmation in the system calling app. In a separate attempt, configure no available handler. | First event says “Sent to calling app.” Second reports the observed local failure for that attempt (Q1). Neither reports an answer, cancellation, duration, or missed call. |
| AC4 | Dial the saved Front desk number, then change the favorite to another number. Select the old event. | Dialer loads the original number. The old event no longer carries that favorite name. No new request occurs until Call or Enter. |
| AC5 | With both lists populated, choose Clear Favorites. Verify the list name, count, and default Cancel. Cancel, then reopen, confirm, quit and relaunch. Repeat for Clear Recents with both lists populated. | Cancel preserves both lists. Confirm empties only the named list, including after restart. A failed clear produces an error and no partial deletion. |
| AC6 | A handoff succeeds but writing the event fails. Retry the write twice. | The UI distinguishes the handoff result from the storage error. At most one history event is committed. The calling app receives exactly one request. |
| AC7 | Clear Recents while a logged request is pending, then receive its completion. Start another call afterward. | The cleared attempt does not reappear. The new eligible attempt appears once. |

## Favorites local acceptance

Verified locally on 24 November 2026 with AppKit tests, a stub calling app, and temporary storage reopened to verify persisted data.

- [x] **F1 Add.** Blank and prefilled editors, required name and valid number, duplicate lookup after normalization, cancel, and persistence. Covers T6 and AC1.
- [x] **F2 Select.** Selection loads the number for review and preserves history. Browsing keeps the draft and the popover opens on Dialer. Covers the selection part of T3 and T5.
- [x] **F3 Call.** Explicit Call and Enter, pending and completed attempts, duplicate-submission protection, observed handoff failures, and storage retry without another call. Covers T1–T4, T10–T11, and AC6 with a stub handoff.
- [x] **F4 Edit.** Validated edits, same-number formatting, collision feedback, retry with the draft retained, and current names in Recents. An old attempt and a loaded Dialer draft keep the original number. Covers AC4.
- [x] **F5 Delete one.** The confirmation identifies the target and defaults to Cancel. A failed deletion can be retried. A confirmed deletion persists and keeps the existing recent attempt and Dialer draft. Covers the Favorites portion of T9.
- [x] **F6 Clear list.** The confirmation names Favorites and shows the count. Cancel or a write failure preserves the list. Clearing persists and keeps Recents and the Dialer draft. Covers the Favorites portion of AC5.

AppKit layout checks verify that both lists use the available width, display metadata beneath the title, and align actions at the trailing edge. Rendered AppKit previews were compared with the mockup in light and dark appearance. Real-device call acceptance is tracked in [Mac + iPhone Acceptance](manual-testing.md).
